# 桌面 AI 悬浮交互系统 —— 技术可行性调研报告

> 调研方式：在目标机器上直接读取三款软件的安装包、进程启动参数与运行时接口，不依赖厂商文档或猜测。
> 调研环境：Windows 11，1920×1200（125% DPI），多显示器。
> 结论时间：2026-10-30

---

## 一、结论摘要

**这套系统可以做，但三款软件的可行路径完全不同，不能用同一套技术硬套。**

| 软件 | 实际形态 | 可用扩展接口 | 可行性 | 推荐路径 |
|---|---|---|---|---|
| **WorkBuddy 5.9.4** | Electron 37 + 内置 CodeBuddy CLI 2.165.0 | ACP 协议、HTTP REST/SSE、会话持久化、Skills/MCP/Hooks | ★★★★★ | 独立悬浮层 + ACP 常驻会话 |
| **DSH（DeepSeek Harness）** | Electron 44 + profile/plugin 体系 + Node 24 | 插件包（`dsh plugin add`）、Web profile 本地 HTTP API | ★★★★★ | 原生插件包 + 本地 API |
| **豆包** | 原生 Chromium 147 外壳（CEF），非 Electron | **未发现任何插件/扩展/本地 API** | ★★☆☆☆ | 只能做桌面辅助程序（UI 自动化镜像） |

一句话总结：**WorkBuddy 和 DSH 都能做到"原生级"集成，豆包做不到。**

豆包的需求里有一条必须先说清楚：**"把豆包原有聊天窗口拆成展示区和输入区"这件事，在不修改豆包程序本体的前提下无法实现。** 它不是一个可以拆分的窗口，是一个渲染整体。可行的替代是"影子界面"——把豆包的对话内容镜像到我们自己的展示窗，再用我们自己的输入框把文字送回豆包。体验接近，但本质是外部模拟，见 §3.3。

## 三、逐款软件可行性

### 3.1 WorkBuddy —— 可行，走 ACP 常驻会话

**关键发现：WorkBuddy 的 AI 引擎不是长在窗口里的，而是一个独立进程。**

GUI 启动时实际执行的是：

```
WorkBuddyAI.exe <cli>\bin\codebuddy --serve --session-id <uuid> --port 0 \
                --permission-mode fullAccess --model ... --mcp-config ... --settings ...
```

也就是说：**会话归属于进程，不归属于窗口。** 这正是需求书第四节"窗口收起后台仍在跑"的天然答案——我们根本不需要去"保住"窗口，只要不去杀进程。

CLI 暴露的接口（`--help` 实测）：

| 参数 | 能力 | 对本项目的价值 |
|---|---|---|
| `--acp` | Agent Client Protocol，stdio 上的 JSON-RPC 流 | 悬浮层可直接作为 ACP 客户端驱动会话 |
| `--serve` | HTTP 服务：REST API + ACP over SSE | 备选通道，适合多客户端 |
| `--session-id` / `--resume` | 会话 ID 固定、跨进程恢复 | 收起/重启后上下文不丢 |
| `--print --output-format stream-json` | 单向流式输出 | 轻量只读场景 |
| `--permission-mode` | 权限模式 | 悬浮层可固定为低权限，避免误操作 |

**推荐架构**：悬浮层进程 `spawn` 一个 `codebuddy --acp --session-id <固定ID>` 子进程，用 JSON-RPC 收发。窗口只是这个会话的一个"视图"，关掉视图不影响会话。

**已验证**：CLI 存在、可执行、参数齐全（`--version` 返回 2.165.0）。
**待打通**：独立启动 CLI 时报 `Authentication required` —— GUI 启动 CLI 时是带着登录态上下文的，我们裸启动没有。这是**唯一的工程卡点，且属于凭据传递问题，不是架构问题**。解决方向有两个：
1. 复用 GUI 的凭据目录/环境变量注入（需进一步定位其 token 落盘位置）；
2. 改为连接 GUI 已经跑起来的那个 `--serve` 实例（端口是动态的，需要从进程参数或端口登记处发现）。

**不建议**：直接改 `app.asar`、注入渲染进程、模拟点击 WorkBuddy 窗口。CLI 已经把接口开好了，没必要走脏路。

### 3.2 DSH（DeepSeek Harness）—— 可行，而且是三款里最规范的

DSH 的 `dsh --help` 直接写着它是什么：

> "boot a DeepSeek Harness profile — an ordered stack of plugin-bundle patch layers under your own overrides."

这是一个**天生插件化**的产品：

- `dsh plugin --profile <name> add <package>` —— 官方插件安装命令；
- `dsh --profile web --port <n>` —— 起一个本地 HTTP 服务，带 `/api` 和浏览器信任围栏；
- `dsh headless "任务"` —— 无界面单次执行；
- `dsh tui --resume <session>` —— 会话恢复。

**推荐架构**：给 DSH 写一个**真正的插件包**（profile patch layer），在插件里挂一个本地 IPC/HTTP 端点供悬浮层调用；悬浮层不需要任何 UI 自动化。这是需求书里"优先使用软件官方支持的扩展方式"的最佳落点。

**待确认**：DSH 的 ACP 入口具体挂在哪个 profile 下（app.asar 里有 `agent_message_chunk` 说明协议已实现，但对外暴露方式需按版本确认）。这属于"读一下就能确定"的工作量，不构成风险。

### 3.3 豆包 —— 只能做外部辅助程序，且必须接受三个硬约束

豆包是原生 Chromium 外壳（`Doubao.dll` + `Doubao.exe`，Chromium 147），不是 Electron，没有 Node 运行时，没有插件目录，没有 CLI，没有可发现的本地 API。**外部程序无法"进入"它的界面。**

需求书要求"复用豆包悬浮球 + 把聊天区和输入区拆开"，技术上只能这样落地：

**影子界面方案（唯一可行）**

```
豆包原生悬浮球（保留，不改）
        │ 用户点击
        ▼
豆包原生聊天窗（被移到屏幕外/最小化，或保持但置底）
        │ UI Automation 读取文本（TextPattern）
        ▼
我们的展示窗（只读镜像，独立拖动缩放）
        ▲
我们的输入框（独立、透明、双击唤醒）
        │ UI Automation 写入 + 触发发送
        ▼
豆包原生输入区（真实发送，保留其全部能力）
```

**三个必须提前接受的约束：**

1. **"拆分"是视觉拆分，不是结构拆分。** 豆包的原生窗口还在，只是被藏起来或挪走了。用户看到的两个窗口都是我们的。
2. **版本脆弱。** 依赖 Windows UI Automation 的控件树，豆包一改版就可能失效，需要跟着维护。这是外部模拟的固有代价，任何方案都绕不过。
3. **不能保证 100% 保真。** 富文本、图片、卡片消息的镜像会失真；语音、通话等能力不在镜像范围内（但也不会被破坏，因为原程序没动）。

**如果这三条不能接受，正确做法是放弃"优化豆包"这个目标**，改为"给豆包做一个并列的悬浮入口"——但那就违背了需求书"不要重复造入口"的要求。这个取舍需要产品侧拍板。

## 四、统一框架设计

需求书建议的"一套统一悬浮框架 + 三个适配模块"是对的，本报告的实现也照此落地。

```
┌──────────────────────────────────────────────────┐
│              统一悬浮框架（本项目）                 │
│                                                  │
│  悬浮球 ──单击──▶ 展开/收起状态机                  │
│  展示窗（独立窗口，独立几何）                       │
│  输入框（独立窗口，透明穿透，双击唤醒）              │
│  全局钩子（鼠标双击 / 热键 / 双击 Enter）           │
│  状态持久化（几何 + 会话 ID + 消息）                │
└───────────────────┬──────────────────────────────┘
                    │ 统一契约 Adapter: start/send/cancel/shutdown
        ┌───────────┼───────────┬──────────────┐
        ▼           ▼           ▼              ▼
   WorkBuddy      DSH         豆包          Demo
   ACP 子进程   插件包+API   UIA 桥接      本地回显
```

**核心设计原则：界面与会话解耦。** 三个窗口是三个独立的顶层窗口，各自持有几何状态，任何一个的显示/隐藏都不触发会话生命周期变化。收起 = `hide()`，不是 `close()`，更不是 `terminate()`。

### 三窗口分离的实现要点

| 窗口 | 特性 | 实现 |
|---|---|---|
| 悬浮球 | 常驻、可拖、不抢焦点、不进任务栏 | 无边框 + `WindowStaysOnTop` + `Tool` + `WindowDoesNotAcceptFocus` |
| 展示窗 | 可拖、可缩放、独立几何 | 无边框 + 自绘圆角 + 边缘命中缩放 + `QSizeGrip` |
| 输入框 | 透明、穿透、双击唤醒 | `WS_EX_TRANSPARENT` + `WS_EX_NOACTIVATE` + 全局鼠标钩子 |

## 五、关键工程问题与解法（均已实机验证）

### 5.1 透明输入框如何"看得见但点不到"

窗口设 `WS_EX_TRANSPARENT` 后，鼠标事件直接穿透到下层程序，**它自己也收不到点击**。所以"双击唤醒"不能靠窗口自己的事件，必须靠**全局低级鼠标钩子** `WH_MOUSE_LL`：

- 钩子只观察、不拦截，永远 `CallNextHookEx`，不影响正常操作；
- 双击判定自己做（两次按下间隔 ≤400ms 且位移 ≤6px），不依赖系统双击消息；
- 命中判定用 `GetWindowRect` 取**物理像素**矩形，与钩子的物理坐标直接比对，规避 DPI 换算误差。

唤醒时用原生扩展样式位热切换（`WS_EX_TRANSPARENT` / `WS_EX_NOACTIVATE` 置位与清除 + `SetWindowPos(SWP_FRAMECHANGED)`），**不 hide/show**，避免闪烁和焦点丢失。

> 实测踩坑：Qt 的 `Qt.WindowTransparentForInput` 切换后窗口看似在前台，但键盘事件收不到——因为 `WS_EX_NOACTIVATE` 的移除没有触发窗口框架重算。必须补 `SWP_FRAMECHANGED`。

### 5.2 双击 Enter 与"Enter 发送"的冲突

判定顺序写死在编辑器的按键处理里：

```
Enter 按下
  ├─ 有 Shift 修饰        → 换行
  ├─ 输入框非空           → 发送（单击 Enter 永远只发送）
  └─ 输入框为空
        ├─ 距上次空 Enter ≤450ms → 收起
        └─ 否则                  → 记录时间，吞掉这次按键
```

三个约束保证不误触：
1. **只在输入框聚焦时生效**——不聚焦时 Enter 归其他程序，绝不全局劫持；
2. **必须为空**——正在打字时连按 Enter 不会收起；
3. **提供替代热键**——`Ctrl+Alt+H` 全局收起、`Ctrl+Alt+Space` 全局唤起，可在配置中改。

### 5.3 DPI 与多显示器

- 全链路按"物理像素"做命中判定（钩子坐标 ↔ `GetWindowRect`），不做逻辑/物理换算；
- 窗口几何持久化用逻辑坐标，恢复时逐屏校验：若矩形不与任何屏幕相交（比如拔掉了副屏），回退到主屏默认位置，不会出现"窗口飞到屏幕外找不回来"。

### 5.4 后台保活

会话归属于适配器进程，不属于窗口：
- 收起只 `hide()` 窗口；
- 适配器（ACP 子进程）全程存活，`done` 信号照常回到展示窗；
- 生成过程中收起，回复继续在后台累积，再展开时完整呈现；
- 进程退出前统一 `terminate` 子进程，不留孤儿。

## 八、建议的分阶段计划

**阶段一（已完成）** 技术验证 + 统一框架骨架
产出：可运行的悬浮球/展示窗/输入框、全局钩子、状态持久化、适配器契约。

UIA 控件树测绘 → 文本镜像 → 输入回填 → 版本适配层。**建议先做 3 天技术验证再决定是否投入。**

**阶段五** 打包与交付
PyInstaller 单文件 + 开机自启 + 安装包 + 使用说明。

## 九、需要你拍板的三件事

1. **豆包要不要做？** 如果"必须完全保留原生体验且零维护成本"，那豆包这条线应该砍掉；如果能接受"版本升级可能要跟着修"，就按影子界面做。
2. **WorkBuddy 走哪条路？** 独立 ACP 会话（干净、可控，但和 GUI 里的对话是两条线）还是接管 GUI 现有会话（体验统一，但要处理端口发现和凭据复用）。
3. **优先级？** 建议先把 WorkBuddy 打通到可用，再做 DSH，豆包最后。

## 十、架构修订（落地后回看）

第一版按"ACP 常驻会话 / headless 事件流"实现，技术上更干净，但要求用户再登录一次
WorkBuddy CLI、再填一次 DSH 的模型密钥。这与"插件装好就能用"的产品前提冲突，已改掉。

**修订后的结论：不新建会话，接管已登录的窗口。**

三款客户端都是 Chromium 内核（`Chrome_WidgetWin_1`），都能通过 UI Automation 的
`TextPattern` 读到完整对话文本——实测 WorkBuddy 3861 字符、豆包 870 字符。
写入则用"切前台 → 点输入区 → 粘贴 → 写后校验 → 回车"，校验失败自动 `Ctrl+Z` 撤销。

代价与边界：

- 读的是已渲染文本，图片/卡片只能拿到占位符
- 输入区位置按窗口比例估算，客户端大改版需要更新 `PROFILES`
- 写入依赖前台，全屏游戏等场景会被安全阀拦下

换来的是零配置：不用登录、不用密钥、不碰原程序、不改原有会话。

原来的 ACP 与 headless 通道代码保留在 `adapters.py` 中，设置 `OVERLAY_USE_ACP=1`
仍可启用，适合以后做无人值守场景。
